 1. SYSTEM OVERVIEW
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The path-following subsystem enables the robot to autonomously track a
pre-recorded spatial trajectory. The algorithm chosen is Pure Pursuit — a
classical geometric path-tracking method from the autonomous vehicle literature
(Coulter, 1992). Pure Pursuit was selected because:

  - It requires no linearisation of the vehicle model.
  - It is computationally cheap (one nearest-point search + one trigonometric
    transform per control cycle).
  - Its single tuning knob (lookahead distance) has a clear geometric meaning
    and is easy to reason about on hardware.
  - It produces smooth, continuous steering commands even when the robot
    deviates slightly from the recorded path.

The subsystem is structured in three layers:

  Layer 1 — Math kernel    : spursuit.py       (Pure Pursuit geometry, no MQTT)
  Layer 2 — MQTT adapter   : spath_follow.py   (subscribes to Kalman pose,
                                                 publishes rc commands)
  Layer 3 — Mission runner : mqtt_client_path_follow.py  (state machine,
                                                           LED feedback, timing)

┌─────────────────────────────────────────────────────────────────────────────┐
│ skalman.py  — 7-State Extended Kalman Filter                                │
│                                                                             │
│  State vector:  x = [x, y, z, v, omega, yaw, pitch]                       │
│                      m  m  m  m/s rad/s  rad   rad                         │
│                                                                             │
│  Prediction step (linearised kinematics):                                  │
│    x[k+1] = A(yaw, pitch, dt) * x[k]  +  B * u[k]                        │
│    P[k+1] = A * P[k] * A^T  +  Q                                           │
│                                                                             │
│  A matrix key entries (yaw/pitch-dependent):                               │
│    A[0,3] = cos(yaw)*cos(pitch)*dt   (x advances with forward velocity)   │
│    A[1,3] = sin(yaw)*cos(pitch)*dt   (y advances with forward velocity)   │
│    A[5,4] = dt                        (yaw integrates angular velocity)    │
│                                                                             │
│  B matrix (control input: [v_left, v_right]):                              │
│    B[3,:] = [0.5, 0.5]               (linear velocity = mean of wheels)   │
│    B[4,:] = [-1/W, 1/W]             (angular vel from differential drive) │
│             W = track width = 0.23 m                                       │
│                                                                             │
│  Update step (standard EKF):                                               │
│    y = z - H * x_pred              (innovation / residual)                 │
│    S = H * P * H^T + R             (innovation covariance)                 │
│    K = P * H^T * pinv(S)           (Kalman gain)                           │
│    x = x + K * y                   (state correction)                      │
│    P = (I - K*H) * P               (covariance update)                     │
│                                                                             │
│  Measurement vector (17 elements, H is 17x7):                             │
│    Rows  0-6  : Encoder odometry (x, y, z, v, omega_gyro, yaw, omega_enc) │
│    Rows  7-11 : Vision pose  (DISABLED — R set to 1e6)                    │
│    Rows 12-13 : IMU yaw (gyro-integrated, magnetometer)                   │
│    Rows 14-16 : IMU pitch (accelerometer, magnetometer, vision)            │
│                                                                             │
│  Process noise Q (diagonal):                                               │
│    [0.8, 0.8, 0.8, 0.5, 0.5, 0.02, 1e6]                                  │
│     x    y    z    v   ome  yaw  pitch                                     │

 3. TRAJECTORY AUTHORING WORKFLOW
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The Pure Pursuit controller has no internal interpolation — it consumes a
pre-computed dense trajectory. The authoring pipeline is:

  Step 1: DEFINE / CAPTURE SPARSE WAYPOINTS
    Path defined analytically or captured via:
      python3 mqtt_client_teleop.py
    Drive the robot manually; press 'c' at each key pose.
    Output: teleop_waypoints.csv  (columns: x, y, heading — sparse, ~0.5-1 m gaps)
    Convention: +x = right, +y = up (path generation frame).
    Robot is placed at (0, 0) facing the +y direction at path start.

  Step 2: INTERPOLATE TO DENSE TRAJECTORY
    python3 interpolate_waypoints.py
    - Parameterises waypoints by cumulative chord length s.
    - Fits independent cubic splines: x(s) and y(s).
    - Resamples at 0.05 m intervals along the spline arc.
    - Derives heading from spline tangent: heading = atan2(dy/ds, dx/ds).
      (Raw capture headings are discarded — tangent headings are geometrically
       consistent even if the robot wasn't perfectly aligned at capture time.)
    - Converts from path generation frame (+x=right, +y=up, robot faces +y) to
      the trajectory CSV frame (+x=forward, +y=right):
        x_csv = y_input   (forward = up)
        y_csv = x_input   (right   = right)
      Path start is shifted to (0, 0) in the CSV frame.
    - Appends cumulative_dist column (recomputed over converted coordinates).
    Output: trajectory.csv  (columns: x, y, heading, cumulative_dist)

  Step 3: RUN MISSION
    python3 mqtt_client_path_follow.py -s

  Trajectory CSV schema example:
    x,y,heading,cumulative_dist
    0.000,0.000,0.000,0.000
    0.050,0.001,0.020,0.050
    0.100,0.003,0.022,0.100
    ...

 4. PURE PURSUIT — INTUITION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Imagine driving a car on a winding road in the dark. Rather than constantly
reacting to where you are right now, you fix your gaze on a point some fixed
distance down the road and steer toward it. That "gaze point" is the lookahead
point; the fixed distance is the lookahead distance L_d.

The key insight is that any two-wheeled (or Ackermann-steered) vehicle can
reach a nearby goal point by driving along a circular arc. Pure Pursuit finds
the unique circular arc that begins at the robot's current pose and ends at
the lookahead point. The curvature of that arc determines the required
steering angle (or, for a differential-drive robot, the angular velocity).

The lookahead distance L_d is the single trade-off parameter:
  - Large L_d: smooth, less reactive, cuts corners on tight turns.
  - Small L_d: precise tracking, but oscillates and amplifies noise.
  - Rule of thumb: L_d must be at least as large as the tightest turn radius
    in the trajectory, or the controller will become unstable.

In this implementation L_d = 1.0 m, the robot speed is ~0.15–0.30 m/s, and
the trajectory was recorded on a flat arena floor, so the curvature demands
are low enough for stable tracking at that lookahead distance.

 5. PURE PURSUIT — FULL MATHEMATICS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Given:
  Robot pose in world frame:  (x_r, y_r, theta)     [theta = heading, rad]
  Trajectory:                 array of (x_i, y_i, heading_i, s_i)
                              where s_i is cumulative arc length in metres.
  Reference speed:            v  (m/s, set by pathControl())
  Lookahead distance:         L_d = 1.0 m

────────────────────────────────────────────────────
 Step 1 — Find the Nearest Trajectory Point
────────────────────────────────────────────────────

Search over a bounded forward window of SEARCH_WINDOW = 30 points (~1.5 m)
starting from the previously stored nearest index i* to prevent backward jumps:

  i* = argmin  { (x_i - x_r)^2 + (y_i - y_r)^2 }
       i in [i*, i*+30]

where the trajectory y-coordinates are sign-flipped to account for the
coordinate convention difference between the CSV file (+y right) and the
robot/Kalman frame (+y left):

  effective_y_i = -y_i   (CSV convention → robot convention)

This index i* is preserved across control cycles so the search window
slides forward along the trajectory (the robot can never go backward).

────────────────────────────────────────────────────
 Step 2 — Find the Lookahead Point
────────────────────────────────────────────────────

Starting from i*, scan forward until:

  s_j  >=  s_{i*}  +  L_d

The point (x_j, y_j) is the lookahead point in the world frame.
Apply the y sign-flip here as well:

  x_L = x_j
  y_L = -y_j      (trajectory → robot convention)

If the trajectory ends before reaching s_{i*} + L_d, use the final point.

────────────────────────────────────────────────────
 Step 3 — Transform Lookahead to Robot Frame
────────────────────────────────────────────────────

Compute the world-frame displacement:

  dx_w = x_L - x_r
  dy_w = y_L - y_r

Rotate into the robot body frame using the heading theta:

  | dx_r |   |  cos(theta)   sin(theta) |   | dx_w |
  | dy_r | = | -sin(theta)   cos(theta) | * | dy_w |

  dx_r =  cos(theta) * dx_w  +  sin(theta) * dy_w     (forward in robot frame)
  dy_r = -sin(theta) * dx_w  +  cos(theta) * dy_w     (left in robot frame)

────────────────────────────────────────────────────
 Step 4 — Compute the Steering Curvature
────────────────────────────────────────────────────

The geometry of a circular arc from the origin to a point (dx_r, dy_r) gives:

  The chord length squared:
    l^2 = dx_r^2 + dy_r^2

  The radius of curvature R of the unique circle passing through the robot
  origin and the lookahead point (and tangent to the robot's forward axis) is:

    R = l^2 / (2 * dy_r)

  Curvature (inverse radius):

    kappa = 1/R = 2 * dy_r / (dx_r^2 + dy_r^2)

Derivation sketch (chord geometry):
  Place the robot at the origin facing +x. The lookahead point P = (dx_r, dy_r).
  Any circle through the origin and P centred on the y-axis (perpendicular to
  the robot heading) has centre (0, R) and satisfies:

    dx_r^2  +  (dy_r - R)^2  =  R^2

  Expanding:  dx_r^2 + dy_r^2 - 2*R*dy_r = 0
  Solving:    R = (dx_r^2 + dy_r^2) / (2 * dy_r)
              kappa = 2*dy_r / (dx_r^2 + dy_r^2)

Sign convention:
  dy_r > 0  →  lookahead is to the left   → kappa > 0 → turn left
  dy_r < 0  →  lookahead is to the right  → kappa < 0 → turn right

This matches the rc command convention (positive omega = turn left).

────────────────────────────────────────────────────
 Step 5 — Compute and Saturate the Control Command
────────────────────────────────────────────────────

For a differential-drive robot at forward speed v, the required angular
velocity omega to track curvature kappa is simply:

  omega = kappa * v

Saturate to prevent wheel slip (inner wheel reverses above ~1.5 rad/s at low speed):

  omega_cmd = clip(kappa * v,  -MAX_TURNRATE,  +MAX_TURNRATE)
                                   -1.0 rad/s       +1.0 rad/s

Final output:

  rc command:  "rc  {v:.3f}  {omega_cmd:.3f}"

  Published to MQTT topic robobot/cmd/ti at ~50 Hz.

 6. COORDINATE CONVENTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Four frames exist in the system:

  Frame A — Path generation / design frame:
    +x = right
    +y = up  (robot faces +y at path start, placed at origin)

  Frame B — Trajectory CSV frame  (output of interpolate_waypoints.py):
    +x = forward  (= Frame A +y:  forward = up when robot faces +y)
    +y = RIGHT    (= Frame A +x:  right   = right)
    heading: CCW = positive  (stored from Frame A tangent — not used by spursuit.py)

  Frame C — Kalman / Robot internal frame:
    +x = forward
    +y = LEFT  (standard mathematical / ROS convention)
    heading: CCW = positive

  Frame D — Human display (the -s status line):
    y displayed as: -y_Kalman    (so positive = rightward motion, intuitive)
    heading displayed as: -theta_Kalman  (positive = turned right, intuitive)

The Pure Pursuit controller (spursuit.py) bridges B and C by negating the
trajectory y-coordinate before all computations:

  effective_y_traj = -y_csv    (right → left, Frame B → Frame C)

This means the math in Section 5 is fully self-consistent in Frame C.

At mission start, spath_follow.py applies an origin alignment: it translates
the loaded trajectory so its first point matches the robot's current Kalman
pose.  This decouples the abstract path origin (0, 0 in Frame A) from the
encoder-odometry frame, which accumulates from Teensy power-on.

RC command sign rules:
  Positive omega (angular velocity) → turn LEFT
  Negative omega                    → turn RIGHT

 8. KALMAN FILTER — EXTENDED SUMMARY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The Extended Kalman Filter (skalman.py) is the pose estimator that feeds the
Pure Pursuit controller. Key characteristics:

  State vector (7 dimensions):
    x = [ x,  y,  z,  v,  omega,  yaw,  pitch ]
         m   m   m   m/s  rad/s   rad    rad

  Sensor sources fused:
    1. Encoder odometry — x, y, heading, velocity (from spose.py)
    2. Gyroscope        — angular velocity (z-axis)
    3. IMU gyro-integrated yaw
    4. Magnetometer     — yaw and pitch
    5. Accelerometer    — pitch (via atan2(a_x, -a_z))
    6. Vision pose      — CURRENTLY DISABLED (measurement noise R → infinity)

  Prediction model:
    Linearised differential-drive kinematics.
    The A matrix is re-linearised each step around current yaw and pitch,
    making this an EKF (Extended KF) rather than a linear KF.

  Reset behaviour:
    kalman.reset() is called at mission start (drivePathFollow).
    This captures current IMU offsets so the filter starts at

PURE PURSUIT ALGORITHM (implemented in spursuit.py::compute_command):

  Step 1 — Nearest point:
    Search forward in a 30-point (1.5 m) window from the last known nearest
    index i* to avoid backward jumps:
      i* = argmin_{i in [i*, i*+30]}  (x_i - x_r)^2 + (y_i_eff - y_r)^2
    where y_i_eff = -y_i_csv  (sign flip for coordinate convention).

  Step 2 — Lookahead point:
    Advance from i* until cumulative arc length exceeds s_{i*} + L_d:
      j = min { j : s_j >= s_{i*} + L_d }
    Lookahead coordinates: (x_L, y_L) = (x_j, -y_j_csv).

  Step 3 — Transform to robot frame:
    dx_w = x_L - x_r,  dy_w = y_L - y_r
    dx_r =  cos(theta)*dx_w + sin(theta)*dy_w   (forward component)
    dy_r = -sin(theta)*dx_w + cos(theta)*dy_w   (lateral component, +left)

  Step 4 — Curvature (chord geometry derivation):
    The unique circle tangent to the robot's heading and passing through
    (dx_r, dy_r) has radius:
      R = (dx_r^2 + dy_r^2) / (2 * dy_r)

      kappa = 2 * dy_r / (dx_r^2 + dy_r^2)
    Sign: kappa > 0 => turn left; kappa < 0 => turn right.

  Step 5 — Control command:
